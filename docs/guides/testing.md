# Testing

| Layer | Where | How |
|---|---|---|
| Core (recurrence, iCalendar, queries, emoji validation, list presentation) | `tests/Wintodo.Core.Tests` | xunit v3, pure functions; presentation cases under `Presentation/` |
| Data (store, migrations, perf assertions, iCal import/export) | `tests/Wintodo.Data.Tests` | xunit v3, temp-file SQLite per test (`StoreFixture`) |
| Sync (CalDAV client and sync service) | `tests/Wintodo.Sync.Tests` | xunit v3, fake HTTP handler |
| App shell and features | `tests/ui/*.ps1` | `winapp ui` (UI Automation) scripts against the running packaged app |
| Accessibility | `tests/ui/m8-design-accessibility.ps1` | `winapp ui` audit, gated at zero errors |
| Performance | `scripts/Measure-Perf.ps1` | see [performance.md](performance.md) |

## Unit tests

```powershell
dotnet test Wintodo.sln -p:Platform=x64                                   # everything, ~10 s after build
dotnet test --project tests/Wintodo.Data.Tests -p:Platform=x64 --filter-class "*MigrationAndListTests"
dotnet test --solution Wintodo.sln -p:Platform=x64 --report-trx --coverage  # what CI runs
```

The test projects are xunit v3 executables on Microsoft Testing Platform
(`global.json` opts `dotnet test` into MTP). VSTest options such as `--logger` and
`--filter "FullyQualifiedName~…"` do not apply; use `--report-trx`, `--coverage`,
`--filter-class`, `--filter-method`. Every call that accepts a `CancellationToken`
passes `TestContext.Current.CancellationToken` (analyzer xUnit1051, an error here).

CI uploads `SafeTestResults/summary.json`, generated by
`scripts/Export-SafeTestResults.ps1`, with only fixed suite labels and validated
total/executed/passed/failed/skipped/unresolved counters. Raw TRX, coverage and
debugger output can contain local paths or failing-test values; keep those
artifacts private. The exporter fails for missing/duplicate/malformed reports
and preserves failure/skip counts. Its marker and invalid-report regression is
`tests/scripts/Test-SafeTestResults.ps1`. Export does not replace the MTP exit
code or make failed/skipped tests pass.

Rules:
- Anything date-dependent takes `IClock`. Never call `DateTimeOffset.Now` outside
  the clock implementation.
- Data tests use a fresh temp database per test; never a shared file.
- Data test helper connections use `TestSqliteConnections.Create` with pooling
  disabled. Fixture cleanup clears only its own production writer/read-only
  pool keys through `ClearStorePools`; do not clear process-wide pools while
  other tests run. Keep the exact key format aligned with the production store.
  [The isolation record](../plans/dep15-sqlite-test-pool-isolation.md) contains
  the reproduced failure and deterministic cleanup regressions.
- New iCalendar behaviour gets a fixture in `tests/fixtures/ical/` and a
  round-trip assertion. Unknown properties must survive byte-for-byte.
- Import behaviour (ADR-016) is tested in `tests/Wintodo.Import.Tests`: the
  converters, the Graph client against `FixtureGraphHandler`/scripted handlers,
  the mapper, and real-store re-import scenarios (`ImportStoreTests`). A new
  Graph field gets a fixture change in `tests/fixtures/mstodo/` and an assertion.
- Perf assertions (10 000-task query ≤ 5 ms, search ≤ 60 ms) live in
  `SmartListPerformanceTests` / `PerformanceFixtureTests` — keep them green.

## UI gate scripts

**Main-machine policy:** UI automation runs in the `WintodoTest` Hyper-V VM through
`scripts\Invoke-VmGate.ps1` ([ADR-013](../adr/ADR-013-hyperv-test-vm.md); see
[Running gates in the test VM](#running-gates-in-the-test-vm)). Builds and unit
tests run on the host while the owner works. A gate the VM cannot run yet stays
pending. Never silently fall back to the owner's desktop. The UI scripts refuse to
run unless `WINTODO_ALLOW_LOCAL_UI=1` is set; `Invoke-VmGate.ps1` sets it only
inside the guest. The loopback CalDAV server alone does not require this opt-in.

The scripts themselves are target-agnostic local scripts: UIA, input injection,
file paths and process cleanup all act on the machine they run on. That is why
they run whole inside the guest instead of being driven from the host. Merely
adding `--on sandbox` to `winapp run` would leave later commands acting on the host.

Only with explicit owner permission for that session may a gate run on the host.
Use a fresh PowerShell window, set the process-only opt-in and restore it in `finally`:

```powershell
$previousLocalUi = $env:WINTODO_ALLOW_LOCAL_UI
try {
    $env:WINTODO_ALLOW_LOCAL_UI = '1'
    .\tests\ui\run-undo-gate.ps1
} finally {
    $env:WINTODO_ALLOW_LOCAL_UI = $previousLocalUi
}
```

Agents must obtain permission before setting this opt-in on the main machine;
never persist it in a user/machine environment variable or shell profile. Run
one desktop workflow at a time. Local synthetic input moves the real cursor and
changes focus; contrast and reduced-motion gates also change Windows settings.

Each `run-*-gate.ps1` launches the **already-built Debug x64 output**
(`src\Wintodo.App\bin\x64\Debug\net10.0-windows10.0.26100.0\win-x64`) with
`winapp run <folder> --detach --json`, points it at a throwaway database under
`tests\ui\artifacts\<area>\run-<timestamp>\`, runs the matching suite, then
stops the app. Artifacts (results JSON, screenshots, UI trees) are gitignored.

The examples below show the gate scripts; on this machine, run each one through
`.\scripts\Invoke-VmGate.ps1 -Gate <name>`.

```powershell

.\tests\ui\run-m0-gate.ps1                        # launch + m0-smoke, 4 checks
.\tests\ui\run-m8-gate.ps1                        # design + accessibility, 17 checks
```

## Running gates in the test VM

For the schema-compatibility startup gate, create a synthetic schema-7 database
on the host using the Python standard library, then copy only that fixture into
the guest. The generator preserves any existing seed; keep it for subsequent
runs. No live user database is used.

```powershell
python .\tests\ui\New-SchemaGuardSeed.py  # once, if the seed does not exist
dotnet build Wintodo.sln -p:Platform=x64 -warnaserror
.\scripts\Invoke-VmGate.ps1 -Gate run-schema-guard-gate.ps1 `
  -Include 'tests\ui\artifacts\schema-guard\seed-v7.db'
```

The gate runs five checks in one guest session and saves a warning screenshot
and `results.json` under `tests/ui/artifacts/schema-guard/run-*`. Review the
captured warning visually before marking the gate passed.

`WintodoTest` is a Generation 2 Hyper-V VM (4 vCPUs, 8 GB, 80 GB dynamic disk,
Default Switch, Secure Boot, vTPM). Its `clean` checkpoint is a signed-in Windows 11
desktop with Developer Mode, PowerShell 7, the .NET SDK from `global.json` (with
a warm NuGet cache), the Windows App Runtime and the WinApp CLI. Each gate run
restores it, so runs never see each other's state. Your account must be in
**Hyper-V Administrators**; no elevation is needed.

Build on the host first. The guest can't build the app (no Windows SDK/MSVC);
it only builds `tests\Wintodo.Data.Tests` for gates that seed with `dotnet test`.

```powershell
dotnet build Wintodo.sln -p:Platform=x64                       # Debug x64: every run-*-gate.ps1
.\scripts\Publish-Aot.ps1 -Platforms x64                       # only for -Aot and Measure-Perf
.\scripts\Invoke-VmGate.ps1 -Gate run-m0-gate.ps1              # exit code = gate's exit code
.\scripts\Invoke-VmGate.ps1 -Gate run-m13-gate.ps1 -GateArguments '-Aot'
.\scripts\Invoke-VmGate.ps1 -Gate run-m8-gate.ps1 -KeepRunning # leave the VM up to inspect it
```

`-GateArguments` passes arguments through to the gate. `-Include` adds extra
repo-relative files or folders to the copy, such as a baseline under `tests/ui/artifacts`:

```powershell
$baseline = 'tests\ui\artifacts\completion-measure\vm\timings.json'
.\scripts\Invoke-VmGate.ps1 -Gate run-completion-measure.ps1 -GateArguments `
    '-AppDirectory', 'C:\wintodo\src\Wintodo.App\bin\x64\Debug\net10.0-windows10.0.26100.0\win-x64', `
    '-ArtifactDirectory', 'C:\wintodo\tests\ui\artifacts\completion-measure\vm'
.\scripts\Invoke-VmGate.ps1 -Gate run-completion-motion-gate.ps1 `
    -GateArguments '-BaselineTimings', $baseline -Include $baseline
```

`Invoke-VmGate.ps1` does six things:
1. Restores `clean` and waits for the guest console desktop to be signed in and
   unlocked.
2. Copies files into `C:\wintodo` in the guest at their repo-relative paths, so
   gates run unchanged:
   - every tracked (or untracked, not ignored) file;
   - the Debug x64 output;
   - `publish\aot\win-x64` when the gate gets `-Aot`.

   It leaves out each output's `Wintodo.build.appxrecipe` (absolute host paths;
   `winapp run <folder>` fails on it) and `AppX\`. winapp then lays out the folder
   itself in the guest.
3. If the gate calls `dotnet test`, builds `tests\Wintodo.Data.Tests` in the
   guest first; some gates pass `--no-build`.
4. Runs the gate with pwsh 7 in the guest's desktop session. A PowerShell Direct
   session has no desktop, so it uses a one-shot scheduled task with
   `LogonType Interactive`. `WINTODO_ALLOW_LOCAL_UI=1` exists only in that guest process.
5. Copies the guest's `tests/ui/artifacts` into `tests/ui/artifacts/`, the gate's
   console output into `tests/ui/artifacts/vm/<gate>-<timestamp>.log`, and
   `docs/PERF.md` if the gate changed it (unless the host copy changed meanwhile).
6. Turns the VM off (unless `-KeepRunning`) and exits with the gate's exit code.

Only one run at a time; a second concurrent run fails immediately. Gates may
change Windows settings in the guest (contrast, animations); the next restore
discards them.

The real Share fixture is a BCL-free native C++ desktop source using the Windows
DataTransferManager HWND interop. Build it on the host with
`scripts/Build-ShareSource.ps1`, then run
`scripts/Invoke-VmGate.ps1 -Gate run-share-gate.ps1 -GateArguments '-Aot' -Include 'tests/ui/artifacts/share-source'`.
All activation, discovery and input stay in the guest. AOT shares use the disposable
guest package's LocalState. Direct mapping tests do not prove broker activation.

In a fresh guest the app's first launch takes 11–12 s (package registration, cold
file cache, Debug JIT), longer than most suites' window waits. So before a UI
gate, `Invoke-VmGate.ps1` launches the same output once, waits for the window,
closes it and runs `Reset-AppxPackage`. The gate then gets a warm launch with
first-run app data. `-NoWarmup` skips this; `Measure-Perf.ps1` never warms up.
New runners should still `winapp ui wait-for` a stable element before asserting.
M5 restart waits up to 15 seconds for the Sort control before inspecting the
window; the earlier three-second window poll could expire on the VM before the
restarted app became ready.

The guest runs Windows build 26300; system dialogs can differ from newer host
builds. For example, the file dialog's Open control (id 1) is a Button there but
a SplitButton on 28020. Match such controls by AutomationId, not by type.

M8 restores the saved High Contrast preference as well as flags and all system
colours. With an originally empty, inactive scheme, Windows retains the last
scheme name in its SPI cache even after the empty registry preference is restored;
the harness checks that preference instead of requiring an unachievable empty
cached name. Named or originally active schemes still require exact SPI equality.
The original/restored values are saved in `contrast-restoration.json`.

Undo keyboard checks focus a row or the list menu button; focusing the ListView
itself can fail its CLI focus confirmation after selection changes. List deletion
restoration uses Ctrl+Z so slow VM CLI calls cannot exhaust the snackbar lifetime.

**Performance:** `-Gate Measure-Perf.ps1` copies the framework-dependent Release
build and `publish\aot\win-x64`, builds the Release test project in the guest and
adds `-SkipBuild`. Build both on the host first, exactly as `Measure-Perf.ps1`
does without `-SkipBuild` (see [performance.md](performance.md)). VM rows are a
different environment from earlier host rows. Pass a `-Milestone` label that
says so (for example `M9-VM`) and compare only like with like.

**Watching the VM:** `vmconnect localhost WintodoTest` (host enhanced session
mode is off, so VMConnect uses the guest console). Without a viewer, capture the
guest screen through Hyper-V instead:
`. .\scripts\TestVm.Common.ps1; Save-TestVmScreen -VmName WintodoTest -Path screen.png`.
The gate runner refuses to start if the console isn't signed in and unlocked.

**Still manual:** m7 toast Complete/Snooze (`-VerifyToastCompletion`/`-VerifyToastSnooze`)
needs someone to act on a real toast, and the reboot-persistence row needs a reboot.
Use `-KeepRunning` and VMConnect for those.

### Building the VM (once)

1. `.\scripts\New-TestVm.ps1 -IsoPath <Windows 11 x64 ISO>` creates the VM
   (rolls back on failure).
2. `.\scripts\Install-TestVmWindows.ps1` installs Windows 11 Pro unattended
   (about 15–25 min). Details:
   - It creates the local administrator `tester` and generates the password.
   - The credential is saved with DPAPI to
     `%LOCALAPPDATA%\Wintodo\WintodoTest.credential.xml`; never in the repo.
   - It types the DVD boot-prompt key into the VM's virtual keyboard, not the host.
   - If you change the guest password by hand, re-save it with
     `.\scripts\Set-TestVmCredential.ps1` in your own terminal.
3. `.\scripts\Initialize-TestVm.ps1` prepares the guest and takes `clean`.
   It sets up:
   - automatic sign-in (the password is an LSA secret in the guest);
   - no lock screen, screen saver or sleep, and no automatic update restarts;
   - a 1920 × 1080 display and Developer Mode;
   - PowerShell 7, the .NET SDK (SHA-512-checked) and the Windows App Runtime and
     WinApp CLI versions from `Directory.Packages.props`;
   - a NuGet cache warmed for `tests\Wintodo.Data.Tests`;
   - the public part of `publish/msix/m10-test.cer` in `LocalMachine\TrustedPeople`.

Re-run `Initialize-TestVm.ps1 -Force` after bumping `global.json`,
`Microsoft.WindowsAppSDK` or the WinApp CLI, or after regenerating the M10 test
certificate. It restores the old `clean` first, so gate leftovers never get captured.

## AutomationIds are API

Every interactive element has `AutomationProperties.AutomationId` named
`Todo.<Area>.<Element>` (e.g. `Todo.List.AddTaskBox`, `Todo.Row.CompleteToggle`,
`Todo.Settings.Sync.Connect`). The UI scripts select by these ids. Renaming one
breaks a gate — search `tests/ui/` before you change an id.

The import-removal dialog assigns `Todo.Import.RemoveConfirm.Primary` and
`Todo.Import.RemoveConfirm.Close` when its template is applied, so default-button
style changes cannot replace those IDs. The import gate acquires a main HWND
belonging to the launched PID before readiness checks and cleans up failed
launches before starting another process; failure evidence must not use an old HWND.

## Writing a new UI suite

1. Load `/winui-ui-testing`. Generate **one** batch script covering assertions,
   interactions and the accessibility audit; run it in a single pass.
2. Follow the existing shape: `param([int]$AppPid, [string]$ArtifactDirectory)`,
   a `Test-UI` helper counting pass/fail, results written to
   `$ArtifactDirectory\results.json`, non-zero exit on any failure.
3. Add a `run-<area>-gate.ps1` that launches with a scratch `--database-path`
   (and `--clock-file` if time matters) and always stops the app in `finally`.
   Scratch databases skip the onboarding Welcome surface; pass
   `--show-onboarding` to test it. Debug builds also accept
   `--trace-file <path>`, which writes the app's trace lines (unhandled and
   command exceptions, binding failures) next to the gate's artifacts.
5. If `winapp ui invoke` reports "does not support any invoke pattern" for a
   button the capture shows as invokable, the bound command threw: WinRT
   swallows the exception at the `ICommand` boundary and the button stays
   drawn as pressed. Capture a trace and fix the product; don't retry.
6. Record the gate result in `docs/PROGRESS.md`. A partial pass is reported as
   partial, naming what failed.

## CI

`.github/workflows/ci.yml` builds x64 Debug with warnings as errors and runs the
four Microsoft Testing Platform projects on `windows-2025`. CI exports reviewed
suite counters and redacted scanner/dependency/toolchain evidence; raw TRX,
coverage and logs stay private. UI gates need the test VM's interactive desktop
and Developer Mode. See [ci.md](ci.md) for dependency and runner policy.

On `v*` tag pushes and scheduled/manual main runs, a separate release matrix
publishes Native AOT and packages unsigned x64 and ARM64 MSIX artifacts after
build/test succeeds. Ordinary main pushes and PRs run build/test and security
checks. Production signing and install/uninstall gates remain open; see
[packaging.md](packaging.md).
