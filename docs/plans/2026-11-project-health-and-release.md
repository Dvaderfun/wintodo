# Wintodo: November review and prioritized work

Review: 20–21 November 2026. Audit baseline: `2a836a0`; implementation branches start at `5c61a66`, which preserves the subsequent scroll-gap fix. A checked box means there is evidence for that specific action. A fix is not complete merely because a branch exists.

Wintodo is in the Store. The workstation has the Store-signed 1.0.1.0, and the [milestone ledger](../PROGRESS.md#current-state) records M0–M5 complete and automated gates for iCalendar, reminders, accessibility, CalDAV and import. Native AOT works, but full idle-memory and native ARM64 runtime measurements are open. The next work that most directly benefits users is to prevent lost edits and task metadata; styling changes and a new implementation language rank below that. No breach was established by this source and dependency review. It was not an investigation of deployed systems or customer records.

## 1. Prevent loss of user data

These four fixes are implemented and included in signed DEV 1.0.1.188. See the [original handoff and acceptance cases](2026-11-sol-integrity-handoff.md) and the [verified DEV update](../PROGRESS.md#m10--signed-dev-update-with-data-integrity-fixes-2026-11-21).

- [x] **P1 — Preserve alarms, category links and attachment references on inline rename and star.** List queries return scalar projections. The [row commands](../../src/Wintodo.App/ViewModels/TaskListViewModel.Tasks.cs) send them through [whole-task collection replacement](../../src/Wintodo.Data/SqliteTaskStore.Tasks.cs). Use narrow transactional updates. Verify both commands on a freshly queried row with all three collections and reopen the database to check the result.
- [x] **P1 — Save pending edits when switching tasks or closing.** The [detail loader](../../src/Wintodo.App/ViewModels/TaskDetailViewModel.Persistence.cs) cancels title/note debounce before replacing the model. Drain edits against their original UID; exercise fast selection and window close at both debounce boundaries.
- [x] **P1 — Bind attachment cleanup to its owning database.** [Startup](../../src/Wintodo.App/App.xaml.cs) can select an environment-overridden database while passing the package's real attachment root to [cleanup](../../src/Wintodo.Data/SqliteTaskStore.ImportCleanup.cs). Validate the effective database/root pair. Test separate real and scratch fixture roots; never test deletion with customer files.
- [x] **P2 — Preserve attachment ownership across awaits.** [Attachment copy](../../src/Wintodo.App/ViewModels/TaskDetailViewModel.Attachments.cs) reads the active model before and after I/O. Capture the original task through selection, copy, persist and rollback. Change selection during a deliberately delayed fixture copy; both tasks must reopen correctly.

## 4. Improve measured performance before considering Rust

- [ ] **Measure full-list retention first.** At 10,000 tasks the [recorded](../PERF.md) best warm smart-list queries took 1.519–2.652 ms; worst warm FTS5 search took 6.694 ms. The [smart-list benchmark](../../tests/Wintodo.Data.Tests/SmartListPerformanceTests.cs) caps results at 100. Measure opening All with 20,000 tasks, switching back and repeating. Record p50/p95 first render, retained row count, private working set and 10-minute idle; separate x64 and ARM64 evidence.
- [ ] **Bound rows retained after navigation.** The [list cache](../../src/Wintodo.App/ViewModels/TaskListViewModel.Loading.cs) retains visited row models for the life of the shell. Preserve active edits, selection and viewport; compare the measurements above before and after.
- [ ] **Reduce reorder and export I/O.** A manual move rewrites visible active rows in separate transactions. Use existing sort-key gaps and rebalance atomically when necessary. Export hydrates each task's tags, alarms and attachments with separate queries; measure a large export and batch by list within a consistent read snapshot if it is material.
- [ ] **Only prototype Rust when profiling identifies a CPU bottleneck.** The app already uses Native AOT and native SQLite/FTS5. Rust does not shorten a retained object's lifetime or reduce transactions. Require a representative workload, an end-to-end improvement on both architectures and a packaging/maintenance cost comparison before adding an FFI boundary.
