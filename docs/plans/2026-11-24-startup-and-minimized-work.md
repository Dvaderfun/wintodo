# Open at the saved size and keep minimized work useful

Investigation of signed x64 DEV `1.0.1.245` (app source `486482f5`), 24 November 2026. The [VM observations](../PERF.md#2026-11-24--startup-and-minimized-idle-on-signed-dev) cover a returning user with one local task. The changes below are recommendations.

## Why the window opens twice visually

1. The [window constructor](../../src/Wintodo.App/MainWindow.xaml.cs) sizes the window to the 1180 × 820 DIP default. At this point the title bar exists but its [content frame](../../src/Wintodo.App/MainWindow.xaml) has no page. [Normal launch](../../src/Wintodo.App/App.xaml.cs) activates the window and explicitly awaits a `CompositionTarget.Rendering` callback **before even starting** SQLite initialization or interrupted-import recovery.
2. Window initialization then attaches `ShellPage`. The [five placement settings](../../src/Wintodo.App/Services/ShellStateService.cs) are read sequentially. Although the placement read runs alongside [shell initialization](../../src/Wintodo.App/Pages/ShellPage.Lifecycle.cs), the window waits for **both** before applying the saved bounds. The initial list is behind navigation, appearance, onboarding and sync-settings reads. Those sync-settings reads are local; the list does not require a reply from a CalDAV server.
3. A maximized session takes a further step: normal bounds are applied first, and `ApplyDeferredPresenterState()` is called only after Windows integration (reminders, badge, jump list) and any launch routing. It even comes **after** the existing `WINTODO_PERF_INTERACTIVE_MS` marker. That marker cannot tell us whether the user was still watching the window expand.

**The preview also loses maximization.** `MainWindow` uses `AppWindow.Presenter is OverlappedPresenter` to set the minimum size, track normal bounds, maximize, and decide what to save on close. In the signed DEV executable the restore method reads the presenter and returns: there is **no call to maximize**. The close path **always writes `false`** to the maximized field; the minimum-size setters are also absent. This matches [CsWinRT issue 1930](https://github.com/microsoft/CsWinRT/issues/1930) and [WinUI issue 10471](https://github.com/microsoft/microsoft-ui-xaml/issues/10471). The [VM and binary checks](../PERF.md#2026-11-24--startup-and-minimized-idle-on-signed-dev) distinguish this from a merely delayed maximize or a slow database write.

For the main window's overlapped presenter, check `Presenter.Kind` and use the explicit WinRT projection, `presenter.As<OverlappedPresenter>()` (`using WinRT`), consistently on all four paths. The upstream reports verified that workaround. Capture state while the window is still live; verify maximized and normal close/reopen and the minimum size in a **published Native AOT** candidate. A Debug-only pass cannot verify this fix.

**First change to try:** Start the existing background SQLite open while constructing the window. After the schema check succeeds, read placement early, independent of list initialization; use one read for the saved bounds and maximized flag if the separate reads prove material. Attach the real shell, apply valid normal bounds while hidden, and, for a saved maximized session, maximize at the point of first show and activate in the same UI turn. Use the default only if there is no usable placement. Preserve the normal bounds for Restore Down. Treat `Maximize()` as potentially showing the window; don't call it and then wait for I/O before attaching the shell.

**Next, shorten time to the selected list.** Start the selected-list read as soon as the necessary local state is known. Show the shell immediately and populate it asynchronously, as [DESIGN](../DESIGN.md) requires. Avoid briefly showing My Day or “no tasks” when a different list is loading. The first-run Welcome decision and saved theme affect what the user should see; sync settings, options for other lists and Windows integration do not all need to finish first. Measure their individual costs before moving them. Keep import recovery ordered against new writes/imports and preserve the read-only rejection of a newer database, notification actions without a window, and Share Target activation.

Validate fresh processes with saved normal and maximized bounds, first run, a populated saved list, Restore Down, different DPI/work areas, and a newer-schema database. Time **launch to first visible window**, **launch to the correct visible row** and **first accepted input** separately; record the first visible size and any subsequent resize. Check actual presented frames if making a paint claim. Moving a long wait before showing a window can make the first-frame metric look better without making launch faster. Keep [ADR-008's](../adr/ADR-008-perf-budget-rebaseline.md) existing total and app-work budgets.

## What Windows does on minimize

| Task Manager status | What it means for Wintodo |
|---|---|
| Yellow pause: the group contains a suspended UWP process | Windows stops scheduling that process's threads and can later reclaim its memory. Packaged WinUI 3 desktop apps [do not have UWP suspend/resume](https://learn.microsoft.com/en-us/windows/apps/windows-app-sdk/applifecycle/applifecycle). Freezing our own threads would also stop sync and could strand edits or an import. |
| Green leaf: the group contains a process in Efficiency Mode | Task Manager's [Efficiency Mode](https://devblogs.microsoft.com/performance-diagnostics/reduce-process-interference-with-task-manager-efficiency-mode/) combines lower scheduling priority with EcoQoS. Work continues, can take longer, and may use less energy or interfere less with foreground apps. The mode doesn't promise a smaller working set. |

Windows [already assigns lower quality of service](https://learn.microsoft.com/en-us/windows/win32/procthread/quality-of-service/) to a minimized or fully occluded window under its normal policy. A visible window losing keyboard focus is a different case. The lack of a leaf does not establish a power problem.

The local-only DEV process accumulated **no measurable CPU time and no process I/O** in its 30-second minimized sample; the visible-idle and restored-idle samples were equally quiet. The timer below is established by source inspection, not by those short samples. There is no measured reason here to lower priority for the entire app. To evaluate connected accounts, use a separate run spanning multiple 15-minute intervals on a controlled CalDAV fixture. For a battery claim, measure energy on physical hardware.

1. **Don't arm a sync timer without an account.** The [shell](../../src/Wintodo.App/Pages/ShellPage.Lifecycle.cs) currently arms a repeating timer for 15 minutes on every launch. With no account, the [callback](../../src/Wintodo.App/ViewModels/ShellViewModel.Sync.cs) exits without DB or network work. Start on connect and stop on disconnect. This removes four needless callbacks per hour a local-only instance remains running. Keep the existing schedule and resume checks for connected accounts.
2. **Defer screen-only refresh when minimized.** The one-shot local-midnight timer updates the My Day view, row labels and sidebar counts. On an actual minimize, that work can wait until the window is visible again; reuse the date check already used on activation. Likewise, a completed background sync can mark views stale and present updates/conflicts once on return. Continue scheduling OS reminders, updating the badge when needed, and completing outstanding saves, imports and sync. Test restore after midnight and after remote changes, and keep a visible but unfocused window current.
3. **Consider explicit EcoQoS only for measured background CPU work.** [Windows supports process and thread power policies](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-setprocessinformation). Prefer a narrowly scoped background worker where possible. Any process-wide trial should give control back to Windows promptly on restore, and compare CPU time, wakeups, sync completion and first interaction after restore. A leaf, forced working-set trimming, or a short VM CPU sample cannot establish a battery-life improvement.

If idle **memory** is the concern, profile a populated list with a photo separately. Releasing decoded images under memory pressure could reduce retained memory at the cost of decoding them again when the user returns. The one-task run doesn't justify evicting them on every minimize.
